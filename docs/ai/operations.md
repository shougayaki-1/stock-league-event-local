# Event operations playbook

AIが運営スタッフの依頼を受けた場合の標準手順です。AIは手順を読み上げたりチェックリスト化したりできますが、
市場・参加者・景品・サイネージを変更する操作は担当者の承認なしに実行しません。

## 0. 役割と安全な会話形式

AIは次のフォーマットで答えると、スタッフが確認しやすくなります。

```text
観測: 現在確認できた事実
解釈: その事実から分かること（推測は推測と明記）
提案: 次に行う読み取り/操作
影響: 参加者、相場、サイネージ、データへの影響
確認: 人間に確認が必要な点
検証: 操作後に見る画面・ログ・コレクション
```

## 1. 初回セットアップ

### 1.1 事前条件

- Docker DesktopまたはDocker Engine + Compose v2。
- 初回ビルド時だけインターネット（Firebase Emulator、npm、MediaPipeモデル取得）。
- 運営PCの空き容量・メモリ、LANのファイアウォール。
- `.env` に固有の `LOCAL_ADMIN_EMAIL` と16文字以上の `LOCAL_ADMIN_PASSWORD`。

### 1.2 起動

```sh
cp .env.example .env
# .envを編集
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 firebase bootstrap runner web
```

正常状態は `firebase` と `web` が稼働し、`bootstrap` が `Exited (0)`、`runner` が稼働している状態です。
Webは通常 `http://localhost:8098`、参加者ログインは `/login`、管理者ログインは `/admin/login` です。

### 1.3 初回ログイン

1. `/admin/login` で `.env` の初期管理者としてログインする。
2. `/admin/system` の管理者タブで、運営スタッフのアカウントとroleを登録する。
3. `/admin/users` でテスト用参加者を1名作成し、QR/短いIDで `/login` に入れる。
4. `/admin/market` で銘柄が存在するか確認し、`STOP`のままテスト取引が拒否されることを確認する。
5. 必要ならテストデータを削除する。運用開始後のデータを同じ手順で消さない。

## 2. 開場前の準備

### 2.1 システム

- `docker compose ps` とFirebase Emulator UIの状態を確認。
- `data/` のバックアップ先と空き容量を確認。
- 運営PCのスリープ、ブラウザの自動更新、LAN断の可能性を確認。
- 管理者・端末アカウントが正しいroleでログインできるか確認。

### 2.2 市場

- `/admin/system` で初期ポイント、数量プリセット、景品条件を確認。
- `/admin/market` で銘柄名、初期価格、価格フェーズ、CSV取込内容を確認。
- `STOP`状態で、参加者画面が市場停止を表示することを確認。
- 不要な古い銘柄・フェーズ・イベントが残っていないか、削除ではなく一覧で確認する。

### 2.3 参加者

- `/admin/users` で人数、ID、ニックネーム、コースを確認。
- QRや印刷物を少数サンプルでスキャンする。
- 参加者端末の `/login` から入り、Market/Help/Historyが表示されることを確認。
- `isFinished`、`isTicketUsed`、`isInClass` の初期状態を確認する。

### 2.4 シナリオとニュース

- `/admin/news-presets` で表/事後/裏ニュース本文と動画IDを確認。
- `/admin/scenario` でタイムラインの時刻・セッション・対象銘柄・分岐確率・遅延を確認。
- AUTOならrunnerの進行間隔、MANUALならMC担当者と発火手順を確認。
- 各イベントの `signageTargetId` とプレイリスト/動画参照をプレビューする。
- 保存後にイベントが重複していないか確認する。金曜午前自動復元機能はない。

### 2.5 サイネージ

- `/admin/signage-public` で各モニターの名前と公開URLを確認。
- `/admin/signage-playlists` で順序と表示時間を確認。
- 一般モニターを `/signage/public?id=...` で開き、株価・ニュース・音声・動画を確認。
- `/admin/signage-riddle` で部屋、TV役割、初期ステップを確認し、各TVのURLを配布。
- 端末キャッシュを事前に温める。キャッシュ削除は開場直前に行わない。

## 3. 開場・取引開始

1. 受付で参加者を検索し、QR/ID/名前を照合する。
2. 教室利用がある場合は `/terminal/classroom` で入室状態を記録する。
3. 参加者がHelpを読み、ニックネームを設定できることを確認する。
4. MCが開始時刻と最初のニュース/演出を確認する。
5. `/admin/market` または `/admin/scenario` で `RUNNING` へ切り替える。
6. 少数のテスト注文で、見積もり・約定・履歴・ランキング・サイネージ取引表示を照合する。
7. 参加者全体へ開始を案内する。

`RUNNING`へ切り替える操作は市場を開けます。開始予定と担当者の合意がない場合、AIはクリックを指示するだけに留めます。

## 4. 通常運用

### 4.1 参加者から取引を聞かれた場合

- 対象者の短いID/QRと画面上の名前を照合する。
- 銘柄、買い/売り、数量、画面に表示された価格を声に出して確認する。
- 注文後に「成功」と出ても、履歴・残ポイント・保有株が反映されたか確認する。
- タイムアウト時は同じ冪等キーでの確認処理に任せ、別注文を作らない。

### 4.2 シナリオ

- AUTO: タイムライン・runnerログ・`events.isProcessed`・ニュース表示を監視する。
- MANUAL: MCが次のイベントの対象・内容・サイネージ・発火時刻を読み上げてから実行する。
- 発火後は `news`、`public_data/market_for_users`、サイネージ画面を確認する。
- 二重ニュースや価格が動かない場合は、同じイベントを再発火せず、ログと処理済みフィールドを調査する。

### 4.3 サイネージ

- 自動モードは通常プレイリスト/ニュースへ戻る状態を維持する。
- 手動モードは開始・終了・自動復帰を担当者が追跡する。
- 動画再生エラーは、まず端末キャッシュとアセット参照を確認する。
- 長時間端末ではリロードを避け、音声テストは現場の音量を確認してから行う。

## 5. 緊急時

### 5.1 相場・サーバーの異常

1. 影響範囲（1端末/1参加者/全端末/全参加者）を切り分ける。
2. 新規取引を止める必要があるか、担当責任者と判断する。
3. 必要なら市場を`STOP`へ変更する（破壊的/高影響操作として確認を取る）。
4. `/admin/logs`、Firebase Emulatorログ、runnerログ、ブラウザエラーを時刻付きで保存する。
5. 取引は履歴と冪等キーを基準に照合する。ポイントを手計算で上書きしない。
6. 参加者へは「確認中」と伝え、原因不明のまま再注文を促さない。

### 5.2 緊急演出

`/admin/market` またはMCの緊急操作では、上昇/暴落種別、メッセージ、オーバーレイ開始、価格処理のタイミングを確認します。
サイネージの演出だけを直したいのに市場価格まで変更することがないよう、目的を言語化してから操作します。

### 5.3 メディア障害

- 1台だけ: 端末URL、`id`/`roomId`/role、キャッシュ、スピーカーを確認。
- 複数台同時: Emulator/Storage、アセット参照、LAN、Dockerログを確認。
- 動画がない: ライブラリの削除・名前変更履歴と使用先参照を確認。代替動画を明示的に選ぶ。

## 6. 閉場・クロージング

1. MCが最終時刻を告知し、新規注文を停止する。
2. `/admin/market` またはシナリオ制御で市場を`STOP`にする。
3. 未確定参加者、通信中の注文、受付メモ、交換待ちを一覧化する。
4. 全員強制利益確定を使う場合、対象人数とランキングへの影響を人間が確認する。
5. `/admin/users` と `/admin/logs` で最終状態と例外を確認する。
6. `/admin/system` の景品条件と `/terminal/exchange` のチケット使用を照合する。
7. ランキング・取引ログ・参加者一覧をCSV等で保存する。
8. データバックアップを作成し、完了を確認してから必要なら翌日用のリセットを検討する。

リセットは「閉場処理」ではなく、次回運用のための破壊的な初期化です。バックアップ確認と担当責任者の明示承認がない限り実行しません。

## 7. 停止・再起動・バックアップ

### 停止

```sh
docker compose stop
```

データを残して停止します。`docker compose down` はコンテナとネットワークを削除しますが、通常はbind mountの`data/`を残します。
それでも実行前に `data/` が期待場所か確認します。

### バックアップ

1. イベント中の書き込みがない時間に `docker compose stop`。
2. `data/firebase/` を別の安全な媒体へコピーする。
3. `.env`は別管理し、バックアップへパスワードを平文で混ぜない。
4. 復元テスト用の別ディレクトリでコピーを読み込めるか確認する。

### 復元

復元先が正しい空のローカル環境であることを確認し、`data/firebase/`を戻してから起動します。
既存データへ上書きする場合、元データのバックアップと担当者の承認が必要です。

## 8. AIへ依頼するときのテンプレート

```text
目的: 何を達成したいか
対象: URL / 端末 / 参加者ID / 銘柄 / イベントID
現在の状態: STOP/RUNNING/EMERGENCY、AUTO/MANUAL、画面の表示
観測できたログ: 時刻付きで秘密情報を除外
許可する操作: 読み取りのみ / 可逆操作まで / 明示した操作のみ
禁止事項: リセット、削除、再注文など
完了条件: どの画面・ログ・データで確認するか
```

AIが対象・影響・完了条件を復唱できない場合、操作を始めずに質問へ戻ります。
